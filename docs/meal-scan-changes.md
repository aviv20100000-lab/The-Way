# רשימת שינויים: סריקת ארוחות

מסמך עבודה לקודקס. חמישה שלבים, בסדר הזה. כל שלב עומד בפני עצמו וניתן לפריסה בנפרד.
אל תדלג קדימה: שלב 5 מוסיף עומס לשלב שכבר נתקע למשתמשים, והוא מותנה במדידה אחרי שלב 1.

הקשר: הסריקה עובדת ומדייקת בערך ב-80 אחוז. דווח מקרה אחד של היתקעות בשלב
"מצליב מול מאגר משרד הבריאות". השינויים כאן מטפלים בהיתקעות, בשני באגים שפוגעים
בדיוק, ובמעבר לסונט 5.

## שלב 1: טיימאאוט על ההצלבה מול צמרת

**למה:** `matchTzameret` מריצה עד כתריסר שאילתות רצופות לכל פריט, כולל חיפושי
`contains` עם `LIKE %term%`, וכל הפריטים רצים במקביל ב-`Promise.all`. ה-`catch`
בקוד הקורא תופס שגיאה אבל לא תופס תקיעה. זה המועמד הסביר להיתקעות שדווחה.

**קובץ:** `src/app/api/foods/analyze/route.ts`

בתוך ה-`map` שמריץ את ההצלבה (סביב שורה 109), לעטוף את `matchTzameret` בטיימאאוט
ולנפול בשקט לערכי המודל בדיוק כמו שה-`catch` הקיים עושה היום:

```ts
const TZAMERET_TIMEOUT_MS = 2500;

function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T | null> {
  return Promise.race([
    promise,
    new Promise<null>((resolve) => setTimeout(() => resolve(null), ms)),
  ]);
}
```

ואז בגוף ה-`map`:

```ts
const dbFood = await withTimeout(matchTzameret(item.name), TZAMERET_TIMEOUT_MS);
if (!dbFood) return item;
```

**חשוב:** לא לשנות את התנהגות ה-`catch` הקיים. פריט שלא הותאם או שנחתך בטיימאאוט
נשאר עם `source: "ai"`, וזה בדיוק המצב הקיים היום לפריט בלי התאמה.

**לוג:** להוסיף ללוג הטיימינג הקיים (שורה 133) מונה של פריטים שנחתכו בטיימאאוט,
כדי שנדע אם 2500 מילישניות זה הסף הנכון:

```
tzameretTimeouts=${timeoutCount}
```

**בדיקה:** להריץ סריקה על תמונה עם חמישה פריטים ומעלה ולוודא בלוג שהזמן הכולל
לא גדל ושאין `tzameretTimeouts` בתנאים רגילים.

## שלב 2: באג בשאלת "אופן הכנה"

**למה:** כשהמתאמן עונה על השאלה, הקוד בונה שם חדש שמוחק מידע במקום להוסיף.
"חזה עוף" הופך ל"צלוי עוף" ומאבד את "חזה", שזה נתח רזה עם ערכים שונים מהותית
מעוף גנרי. ואם אין מילת בשר בשם, השם הופך ל"צלוי" בלבד, ואז
`normalizeTzameretName` מסננת את "צלוי" כי היא ברשימת `COOKING_STATES`, נשארת
מחרוזת ריקה, ו-`matchTzameret` מחזירה `null` מיד. הפריט יוצא מההצלבה לגמרי.

**קובץ:** `src/components/MealScanner.tsx`, פונקציית `handleDishType` (שורה 135)

**לפני:**

```ts
const meatMatch = currentName.match(/עוף|הודו|טלה|בקר|כבש|עגל|מיקס/i);
const newName = meatMatch ? `${dish} ${meatMatch[0]}` : dish;
```

**אחרי:**

```ts
// צלוי/מבושל/מטוגן/טחון הם צורת הכנה ומצטרפים לשם הקיים.
// שווארמה/קבב הם זהות מנה בפני עצמה ומחליפים אותו.
const PREPARATION_STATES = ["צלוי", "מבושל", "מטוגן", "טחון"];
const newName = PREPARATION_STATES.includes(dish)
  ? `${currentName} ${dish}`
  : dish;
```

**בדיקה:** לסרוק תמונה עם עוף, ללחוץ "צלוי", ולוודא שהשם שנשלח ל-`estimateItemNutrition`
הוא "חזה עוף צלוי" ולא "צלוי עוף". לוודא ששאלת אופן ההכנה עדיין נעלמת אחרי הבחירה
(`needsDishClarification` בשורה 122 בודקת אם השם מכיל את מילות ההכנה, אז השם החדש
מכיל אותן והשאלה נסגרת מעצמה).

## שלב 4: דיוק הזיהוי

### 4א: שער שפיות על ההתאמה מהמאגר

**למה:** ברגע ש-`matchTzameret` מחזירה משהו, ערכי המודל נדרסים לגמרי והפריט מקבל
`source: "tzameret"`, שמתורגם בממשק לחותמת "ערכים ממאגר משרד הבריאות". מצב
`contains` מחפש `LIKE %term%` וממיין לפי `length(name_he) ASC`, כלומר בוחר את השם
הקצר ביותר שמכיל את המחרוזת. ברוב המקרים זו התאמה סבירה, אבל כשהיא שוגה התוצאה
גרועה יותר מהערכת המודל, כי היא מוצגת כסמכותית והמתאמן לא יטיל בה ספק.

**קובץ:** `src/app/api/foods/analyze/route.ts`, בתוך ה-`map` של ההצלבה

אחרי שהתקבל `dbFood` ולפני שמחזירים את הפריט המועשר:

```ts
// ההתאמה מגיעה מחיפוש contains, שיכול לתפוס פריט לא קשור.
// אם צפיפות הקלוריות ל-100 גרם רחוקה מדי ממה שהמודל העריך,
// עדיף להשאיר את הערכת המודל מאשר להדביק חותמת מאגר על מספר שגוי.
const ratio = item.estimated_weight_g / 100;
const modelPer100g = ratio > 0 ? item.calories / ratio : 0;
if (modelPer100g > 0 && dbFood.calories > 0) {
  const factor = dbFood.calories / modelPer100g;
  if (factor > 2.5 || factor < 0.4) return item;
}
```

**לוג:** לספור כמה פריטים נדחו בשער ולהוסיף למחרוזת הטיימינג:

```
tzameretRejected=${rejectedCount}
```

זה יגיד לנו אם הסף נכון. אם הרבה פריטים נדחים, הסף אגרסיבי מדי.

**לא לשנות** את הסף הזה בלי מדידה. 2.5 ו-0.4 נבחרו כדי לתפוס התאמה לפריט לא קשור,
ולא הפרשים סבירים בין הערכת מודל לערך מאגר.

### 4ב: שני כללים לפרומפט

**קובץ:** `src/lib/anthropic.ts`, בתוך `FOOD_PROMPT_TOOL` (שורה 48)

להוסיף אחרי השורה `- Do NOT invent foods. Only include what you clearly see.`:

```
- RULE #3 — ONE SPECIFIC NAME: Give exactly one food name per item. Never return alternatives separated by "/" or "או". If you are torn between two foods, pick the more likely one and lower the confidence instead.
- RULE #4 — SPECIFIC OVER GENERIC: Name the actual food you see (לחם לבן, לחמנייה, פיתה, אורז לבן, פסטה), not a category (פחמימה, ירקות כהים). Use a common generic food name without brands or long descriptions.
- RULE #5 — COOKING STATE: Always end the name with how it was prepared when it is visible: צלוי, מבושל, מטוגן, אפוי, or נא for raw. Raw and cooked differ in calories per 100g, so never omit it for meat, fish, eggs, rice, pasta, or potatoes.
```

**למה כלל 3:** שם כמו "שעועית שחורה / זיתים / ירקות כהים" לא ימצא התאמה במאגר לעולם,
כלומר הפריט מובטח לצאת בלי ערכי משרד הבריאות.

**למה כלל 5:** ב-`src/lib/tzameret.ts` יש כבר לוגיקה שלמה (`cookingStatesOf`,
`COOKING_STATE_INFLECTIONS`, ה-`CASE WHEN` ב-`findBy`) שמעדיפה שורות במאגר שמכילות
את צורת הבישול, כולל טיות. היא נדלקת רק אם השם מכיל את המילה. הכלל הזה מזין מנגנון
קיים ובדוק בלי שורת קוד. בונוס: `needsDishClarification` מחזירה `false` כשהשם מכיל
את מילות ההכנה, אז השאלה למתאמן פשוט לא תוצג על הפריטים האלה.

**לא לגעת** בסכמה `LOG_FOOD_TOOL` (שורה 115). מבנה הפלט נאכף דרכה והשינויים כאן
הם טקסטואליים בלבד.

**בדיקה:** לסרוק את אותן שלוש תמונות בדיקה לפני ואחרי ולהשוות שמות פריטים.
מה שמחפשים: היעלמות של שמות עם לוכסן, והופעה של מצב בישול בשמות של בשר ופחמימות.

## שלב 5: מותנה במדידה, לא לפרוס יחד עם השאר

שני השינויים האלה משפרים דיוק אבל מוסיפים עומס. להיכנס אליהם רק אחרי ששלב 1 בפרודקשן
ולוג הטיימינג מראה שההצלבה יציבה.

### 5א: רזולוציית תמונה

**קובץ:** `src/hooks/client/useFoodTracking.ts` שורה 104 עד 107

ההערה בשורה 104 אומרת ש-1568 פיקסל זו התקרה של Anthropic. זה כבר לא נכון: סונט 5
תומך ב-2576 פיקסל בצלע הארוכה. יותר פיקסלים על צלחת אוכל זה בדיוק מה שמפריד בין
זיהוי "לחם" לזיהוי "וופל".

להעלות ל-2048 כשלב ביניים, לא לקפוץ ל-2576:

```ts
const jpeg = await compressImageToJpeg(file, 2048, 0.9);
```

ולעדכן את ההערה. המחיר הוא יותר טוקני תמונה וזמן העלאה ארוך יותר. למדוד את
`ai=...ms` ואת `size=...KB` בלוג לפני ואחרי. אם הזמן קופץ באופן מורגש, לחזור ל-1568.

### 5ב: סף הביטחון

**קובץ:** `src/lib/anthropic.ts`, בתיאור השדה `confidence` בסכמה (שורה 133)

הסכמה אומרת למודל להחזיר רק פריטים מעל 0.6, אבל ב-`route.ts` שורה 83 כל פריט מתחת
ל-0.6 מסומן `needsManualEntry` ומקבל בורר קטגוריה בממשק (`MealScanner.tsx` שורה 617).
שני התנאים סותרים, אז הבורר כמעט לא נדלק, ופריט שהמודל לא בטוח לגביו פשוט נעלם
מהרשימה.

להוריד את הסף בתיאור הסכמה מ-0.6 ל-0.4, כדי שפריטים לא ודאיים יחזרו מסומנים במקום
להיעלם בשקט.

**זה שינוי התנהגות אמיתי:** יותר פריטים חוזרים, כלומר יותר טוקני פלט ויותר קריאות
`matchTzameret` על השלב שנתקע. לבדוק על לפחות עשר תמונות לפני העלאה, ולמדוד את
`items=` ואת הזמן הכולל בלוג.
